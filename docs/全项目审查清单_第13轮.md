## 1. 🟡 回填漏掉了"只打了上班卡的下午半天假"

**问题**
- `RecalcMealDeductionBackfillAsync` 的第 ③ 步（重算正班工时）只处理**上下班卡都有**的记录。
- 员工上午上班、下午请假、中午没打下班卡时，当初审批回写是按"上班卡 → 请假开始时间"估算工时的（`UpdateAttendanceAfterApprovalAsync` 约 1429 行那一段）。
- 第 ② 步把这类记录的请假小时数改成了新规则的结果，但它的估算工时没有跟着重算，还是按旧请假小时数封顶的旧值。

**复现** ✅复现
- 白班 08:30–17:30，请假 12:00–17:30，08:25 打了上班卡，没打下班卡。
- 旧数据：请假 5.5，工时 min(3.5, 8 − 5.5) = 2.5。
- 回填后：请假改成 **4.5**（扣掉 12:00–13:00），工时仍是 **2.5**。按新规则应为 min(3.5, 8 − 4.5) = **3.5**；把这张假单重新走一遍审批回写，得到的也是 3.5。

**影响**
- 每条这样的记录少算 1 小时工资。
- 触发条件：班次**没配**午间打卡窗口（配了的话页面不让请假从 12:00 开始）、请假从 12:00 左右开始、中午没打下班卡。
- 这次回填已经在生产跑过，受影响的记录已经存在。

**位置**：`Services/Implementations/AttendanceService.cs`
- 约 1633 行 `RecalcMealDeductionBackfillAsync`
- 约 1678 行 `dailyLeaveTotals`、约 1707 行逐日累加（第 ② 步）
- 约 1724 行第 ③ 步（只查上下班卡都有的记录）

**先查生产上有哪些记录受影响**（只读）：

```sql
SELECT u.EmployeeNo, u.RealName, r.WorkDate, r.ClockInTime, r.LeaveHours, r.ActualWorkHours
FROM AttendanceRecord r
JOIN `User` u ON u.Id = r.UserId
WHERE r.WorkDate >= '2026-09-26'
  AND r.AttendanceStatus = 6                 -- 请假
  AND r.ClockInTime IS NOT NULL
  AND r.ClockOutTime IS NULL
  AND r.ApprovalNote LIKE '%按新饭点规则重算请假时长%';   -- 回填第 ② 步改过请假小时数的
```

**改法**（三处，都在 `RecalcMealDeductionBackfillAsync` 里）

```csharp
// ① 第 ② 步：在 dailyLeaveTotals 声明后面加一行，记下每人每天请假从几点开始
var firstLeaveStartByDay = new Dictionary<(int UserId, DateOnly Day), DateTime>();

// ② 第 ② 步的逐日循环里，在 dailyLeaveTotals[key] = ... 这一行后面加：
var segStart = lstart > d.ToDateTime(TimeOnly.MinValue) ? lstart : d.ToDateTime(TimeOnly.MinValue);
if (!firstLeaveStartByDay.TryGetValue(key, out var existingStart) || segStart < existingStart)
    firstLeaveStartByDay[key] = segStart;

// ③ 第 ③ 步的 foreach 循环之后、if (!dryRun) 之前加：
//    只有上班卡的半天假，跟审批回写同一套估算方式，按回填后的请假小时数重新封顶
foreach (var ((uid, day), leaveSegStart) in firstLeaveStartByDay)
{
    var record = await db.AttendanceRecords.FirstOrDefaultAsync(r => r.UserId == uid && r.WorkDate == day);
    if (record is not { ClockInTime: { } ci, ClockOutTime: null } || record.AttendanceStatus != AttendanceStatus.OnLeave) continue;
    if (ci >= leaveSegStart) continue;
    var shift = (await GetShiftAssignmentAsync(uid, day))?.ShiftSchedule;
    var newHours = ApplyLeaveHoursCap(ComputeWorkHours(ci, leaveSegStart), record.LeaveHours,
        ResolveDailyStandardHours(shift, defaultDailyHours));
    if (record.ActualWorkHours == newHours) continue;
    record.ActualWorkHours = newHours;
    record.UpdatedAt = DateTime.Now;
    workHoursChanged++;
}
```

> `db.AttendanceRecords.FirstOrDefaultAsync` 拿到的就是第 ② 步已经改过请假小时数的那条记录（同一个 DbContext 会复用已加载的对象），所以这里读到的 `LeaveHours` 已是回填后的值。

**生产补救**：代码改好后，用上次的独立小工具对 `2026-09-26` 再跑一次回填。先 `dryRun: true` 看"工时改了几条"，数量应该和上面 SQL 查出来的差不多，确认后再 `dryRun: false` 落库。回填可以重复跑，已经对的记录不会变。跑之前照常备份数据库。

**验收**
- 补一个回归测试：上面复现的场景，回填后工时应为 3.5、请假 4.5。
- 原有 `MealDeductionBackfillTests` 的 7 个测试照样通过。

## 2. 🟢 回填后月度汇总没有重新生成

**问题**
- 回填只改了每天的考勤记录，没有重新生成月度汇总。
- 第 ③ 步重算正班工时时，也**没有更新记录的修改时间（`UpdatedAt`）**。"我的记录/我的日历"是靠比较记录的修改时间来判断要不要刷新汇总的（`EnsureMonthlySummaryFreshAsync`，约 1015 行），所以员工打开页面也不会触发刷新。

**复现** ✅复现
- 早退记录 08:25–14:30，旧算法 6 小时，月度汇总总工时 6。
- 回填后记录改成 5 小时，月度汇总仍是 **6**；模拟员工打开"我的记录"后，仍是 **6**。

**影响**
- **发工资用的导出表不受影响**：它直接读每天的考勤记录。
- 受影响的是用月度汇总的地方：月度汇总页、"我的记录/我的日历"、部门汇总接口、智能助手的月度汇总查询。它们在 9 月这部分会显示旧的总工时、加班、请假天数。
- 10 月 1 日 00:10 后台任务会全量重算 9 月汇总，到时自动纠正。

**位置**：`Services/Implementations/AttendanceService.cs` 约 1724–1735 行（第 ③ 步和最后的保存）

**改法**

```csharp
// 第 ③ 步循环里：工时有变化时顺手更新修改时间
if (record.ActualWorkHours != before)
{
    record.UpdatedAt = DateTime.Now;   // 让"我的记录/我的日历"知道这天改过，打开时会刷新汇总
    workHoursChanged++;
}

// 最后保存那里：落库后把回填涉及的每个月的汇总整月重算一次（一次性操作，全员重算可以接受）
if (!dryRun)
{
    await db.SaveChangesAsync();
    var today = DateOnly.FromDateTime(DateTime.Today);
    for (var m = new DateOnly(fromDate.Year, fromDate.Month, 1); m <= today; m = m.AddMonths(1))
        await GenerateMonthlySummaryAsync(m.Year, m.Month);
}
```

**生产补救**（不等 10/1 自动纠正的话，二选一）
- 按第 1 条的补救方法再跑一次回填。带上这段改法后，回填结束会自动重算汇总。
- 或者由总部超级管理员调用 `POST /api/report/generate-monthly-summary?year=2026&month=9`。这个接口已经存在，但**页面上没有按钮**，需要在登录状态下用浏览器开发者工具或接口工具发请求。

**验收**：补一个回归测试，回填后月度汇总的总工时等于回填后记录的工时之和。

## 3. 🟢 审批被拦下后，同一个页面的待审批列表把这张单显示成"已通过"

**问题**
- 上一轮加了"审批时补卡时间还没到就拦下"：抛异常，整个事务回滚，数据库没问题。
- 但回滚之前，内存里的申请单对象已经被改成了"已通过"。页面 `catch` 住异常后，用**同一个数据库上下文**刷新待审批列表，拿到的是内存里那个改过的对象。

**复现** ✅复现：审批被"补卡时间 09-30 08:15 还没到"拦下后，数据库里仍是"待审批"，考勤记录没变；但同一请求里刷新出来的待审批列表，这张单的状态显示为"**已通过**"。

**影响**：只影响这一次页面显示，数据没问题，重新打开页面就正常了。但审批人刚看到"不能审批通过"的提示，列表里却写着"已通过"，容易困惑。

**位置**：`Pages/Approval/PendingApproval.cshtml.cs`，约 62 行（`OnPostApproveAsync`）和约 88 行（`OnPostRejectAsync`）的 `catch (InvalidOperationException ex)`

**改法**：两个 `catch` 里各加一句，丢掉内存里改到一半的对象（批量审批那边约 138 行已经这么写了）：

```csharp
catch (InvalidOperationException ex)
{
    db.ChangeTracker.Clear();   // 事务已回滚，丢掉内存里改到一半的对象，下面刷新列表才会读到数据库里的真实状态
    Message   = ex.Message;
    IsSuccess = false;
}
```

**验收**：审批被拦下后，页面上待审批列表这张单仍显示"待审批"。
