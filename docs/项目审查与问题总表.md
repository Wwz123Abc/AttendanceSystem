## 第三轮复核（2026-09-22，你把剩余条目也改完之后）

这轮把上轮剩下的 8 条（8、26、34、39、40、42、44、45）都处理了：其中 **6 条已改到位**（8、26、34、40、42、45），**2 条确认是我原来的结论有误**（39、44）。

### ⚠️ 但引入了一个新的高危问题（必须处理）——设备管理页的显式事务与重试策略冲突

`Pages/Admin/ZKDeviceManage.cshtml.cs` 这次新增了两处显式事务：

- `:102`（停用设备时清理未确认命令）
- `:130`（删除设备时清理未确认命令）

两处都是直接 `await using var tx = await db.Database.BeginTransactionAsync();`，**没有包在 `db.Database.CreateExecutionStrategy().ExecuteAsync(...)` 里**。

而本项目在 `Program.cs:43` 配置了 `mysql.EnableRetryOnFailure(3)`（失败自动重试 3 次）。**EF Core 的既有约束是：配置了重试策略之后，不允许用户自己 `BeginTransactionAsync`，会直接抛 `InvalidOperationException`。**

**这个坑本项目已经踩过一次**——`ApprovalService.cs:221-225` 的注释写得很清楚：

> ★ 必须通过 CreateExecutionStrategy().ExecuteAsync 包一层：MySql 连接配置了失败自动重试（EnableRetryOnFailure），这种"重试策略"不允许用户自己 BeginTransactionAsync，否则一律直接抛 InvalidOperationException——生产环境这里之前没包这一层，导致每一次审批/驳回（单个和批量）点下去都会 500/400 失败

**预计的实际后果**（需你实测确认）：

- **停用一台设备** → `BeginTransactionAsync` 抛异常 → 被 `catch (Exception ex) { ErrorMessage = $"保存失败：{ex.Message}"; }` 接住 → 界面显示"保存失败：The configured execution strategy 'MySqlRetryingExecutionStrategy' does not support user-initiated transactions…"，**保存不成功**。
- **删除一台设备** → 该 handler **没有 try/catch** → 异常走到全局异常处理 → 返回 **HTTP 400**，页面报错，**设备删不掉**。

**改法**（照抄 `ApprovalService.cs:226-291` 那套写法即可）：

```csharp
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync();
    await db.ZKDeviceCommands.Where(...).ExecuteDeleteAsync();
    db.ZKDevices.Remove(d);
    await db.SaveChangesAsync();
    await tx.CommitAsync();
});
```

或者更简单：**去掉显式事务，改成"先删命令、再删设备"并接受极小概率的中间态**（原来是这个行为，本次改动之前一直是好的）。

> 我无法在本机运行验证这条（没有跑程序、没连数据库），但"`EnableRetryOnFailure` + 直接 `BeginTransactionAsync` = 抛异常"是 EF Core 的既定行为，且本项目已有先例。**请你务必手工点一次"停用设备"和"删除设备"确认。**

### 我判断错的两条（你的实测是对的）

- **第 39 条（`ApplySubmit` 枚举大小写）**：我当时写"`Enum.TryParse` 忽略大小写、后续字符串比较区分大小写，两者不一致"——**错了**。`Enum.TryParse<T>(string, out T)` 这个重载默认是**区分大小写**的（只有带 `bool ignoreCase` 参数的重载才忽略大小写），所以 `ApprovalType=leave` 根本解析不通过、走不到后面的 `if (ApprovalType == "Leave")`，不存在我说的那个不一致。**这条是我误报。**

两条都已按"不是问题"关闭，并记进更新日志 —— 感谢你实测纠正，这正是"引文一致 ≠ 结论正确"的典型例子。
