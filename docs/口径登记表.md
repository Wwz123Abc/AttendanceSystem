## 3. 状态白名单（打卡结果允许覆盖哪些 `AttendanceStatus`）

| 场景 | 上班卡覆盖条件 | 下班卡覆盖条件 | 位置 |
|---|---|---|---|
| 本地/远程打卡 | `Normal / Late / EarlyLeave / NotPunched / Absent`（**白名单**，5 种，不含 `Overtime`） | `Normal / EarlyLeave / NotPunched` | `AttendanceService.cs:167-168` / `:200` |
| 考勤机同步 | `not(OnLeave / Holiday / BusinessTrip)`（**黑名单**，反推等价于 6 种：多了 `Overtime`） | `Normal / EarlyLeave / NotPunched`（跟本地打卡完全一致） | `ZKDeviceSyncService.cs:196` / `:219` |
| 补卡审批回写 / 手动补卡重算 | `not(OnLeave / Holiday / BusinessTrip)` 受保护；受保护外的一律按重新算出的迟到/早退/正常三选一覆盖 | 同左（同一段代码一起处理上下班） | `AttendanceService.cs:1159-1179` |

**结论：⚠️ 有一处细微不一致**：上班卡的"允许覆盖"条件，本地打卡用的是**显式白名单**（枚举 5 种），考勤机同步用的是**黑名单**（排除 3 种，反推出 6 种，多了 `Overtime`）。`AttendanceStatus.Overtime` 这个值目前系统里几乎从未被真正赋值过（`OvertimeThresholdMinutes` 字段本身就没启用，见复审报告"死字段"一节），所以这条差异在当前生产数据下大概率从未真正触发过；但只要以后有任何路径把某天状态设成了 `Overtime`，两条链路对这天"该不该被打卡覆盖"的判断就会不一样。**尚未修复**，建议统一成同一种写法（两边都改成黑名单，或都改成白名单）。

## 4. 下班时间取值规则（同一天收到多次下班候选打卡，以哪一次为准）

| 位置 | 规则 |
|---|---|
| `AttendanceService.cs:192` 本地/远程打卡 | `record.ClockOutTime = punchTime;` **无条件覆盖**——取"最后收到的一次" |
| `ZKDeviceSyncService.cs:202` 考勤机同步 | `record.ClockOutTime is null \|\| r.Time > record.ClockOutTime` 才更新——取"当天所有候选里最晚的一次" |

**结论：❌ 不一致，这是一处真实的口径分歧**（复审报告已指出）。本地打卡如果因为网络重试收到一条"乱序补传"的更早时间（比如两次下班打卡请求，后发的先到、先发的后到），会把已经正确的、更晚的下班时间"倒退"回去，凭空放大早退判定、少算工时；考勤机同步没有这个问题，因为它显式做了"取最晚"的比较。**尚未修复**——建议本地打卡的下班分支也加上 `if (record.ClockOutTime is null || punchTime > record.ClockOutTime)` 的判断，跟设备同步保持一致（需要确认："取最晚"是否是本地打卡这边期望的行为，还是本地打卡场景下"最后收到=最新"本身就应该无条件采信——取决于远程打卡是否可能出现乱序到达，这个我没有十足把握，建议你确认后再改）。

## 5. 工时取整 / 显示精度

| 位置 | 公式 | 用途 |
|---|---|---|
| `AttendanceService.cs:1431` `ComputeWorkHours` 内部 | `Math.Round(分钟/60, 2)` | 单日 `ActualWorkHours` **存库值**——2 位小数 |
| `AttendanceService.cs:1425` `FloorToHalf` | `Math.Floor(h*2)/2` | 月度汇总合计（总工时/加班/夜班/出差工时）——半小时取整 |
| `Helpers/ExcelExportHelper.cs:640` `HalfFloor`（私有） | `Math.Floor(h*2)/2`——**跟 `FloorToHalf` 数学上完全相同，是一份重复实现** | "个人每日明细"报表（`:157-158`）、"打卡时间表"报表（`:426-428`）——每日格子也按半小时取整 |
| `AttendanceService.cs:543`（`GenerateTemplateReportAsync` 内联） | `(int)Math.Floor(h)` | "模板月度汇总表"——每日格子按**整数**取整（舍去小数） |
| `GetPersonalAttendanceAsync`/`ToDto`（`:1567` 附近） | 不额外取整，原样返回 `ComputeWorkHours` 已经 `Round(x,2)` 过的值 | "我的记录"页日明细——2 位小数 |

**结论：❌ 至少 3 种精度共存（2 位小数 / 半小时 / 整数），其中一处是同一张报表内部自相矛盾**：模板月度汇总表自己的"每日格子"用整数取整，自己的"合计"列却用半小时取整——同一份数据在同一张表里，把每天的格子加起来，不一定等于表尾的月合计（相差可以到大半个小时/天，天数一多会更明显）。`HalfFloor`/`FloorToHalf` 两处重复实现虽然数学结果一样，但维护上是两份代码，以后改取整规则（比如改成向上取整）容易漏改一处。

**建议（未处理，需要你确认方向）**：
1. 删掉 `ExcelExportHelper.HalfFloor`，改成直接调用 `AttendanceService.FloorToHalf`——这条零风险，随时可以做。
2. 模板月度汇总表的"每日格子"要不要也从整数改成半小时取整（跟合计口径统一）——这是个**产品决策**：改了之后格子上可能出现"8.5"这种带小数的显示，需要确认是否符合参考模板的格式要求，我没有替你改。

## 6. 请假时长（今日已统一，此前是两套独立公式）

| 位置 | 说明 |
|---|---|
| `AttendanceService.cs:1453` `ComputeLeaveHoursForDay(day, leaveStart, leaveEnd, lunch, dinner, dailyCapHours)` | **唯一口径**：算请假区间落在这一天里的重叠小时数，再用这天的标准工时（`dailyCapHours`，没排班用公司默认标准工时）封顶 |
| `ApprovalService.cs` `SubmitApprovalAsync` | 提交申请时，逐日调用这个函数累加，算出"预估总时长"（`LeaveDurationHours`），显示在申请单上 |
| `AttendanceService.cs` `UpdateAttendanceAfterApprovalAsync` 请假分支 | 审批通过后，同样逐日调用这个函数，把每天的 `LeaveHours` 写回考勤记录 |

**结论：✅ 今天（09-17）之前，这两处是完全独立的两套公式**（提交时直接套用整段起止时间跑一遍工时公式，回写时用"这一天 0 点到 24 点"的交集跑同一个工时公式）——**跨天请假中间的整天会被算成 22.5 小时**这种明显错误的数字，且提交时的预估总时长和回写后逐日累加的总数还对不上（比如一张 3 天的假单，提交预估 44.5 小时，逐日累加只有 41.5 小时）。已经在今天的修复里统一成同一个函数，两处口径现在保证一致，并补了单元测试（`AttendanceSystem.Tests/LeaveHoursTests.cs`）锁定行为。
