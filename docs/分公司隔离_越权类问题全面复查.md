## 1. 结论摘要

上次发现的"待确认登记列表不过滤"问题只是冰山一角。同类问题集中在两类根因：

1. **写入侧缺范围校验**（按 id 操作前没查记录归属部门）：待确认登记认领/驳回、公告撤下/已读查询、审批兜底人、月度汇总重算、考勤组写权限判定。
2. **隔离未覆盖的通道**：匿名设备推送（/iclock）、角色级文件访问端点、员工可达的全局重算入口。

**风险定级：3 个高危（H）、9 个中危（M）、约 10 个低危（L）与口径问题。** 建议上线（录入真实员工）前修复 H1/H2/H3，随后处理 M 级。

## 2. 角色模型与判定规则（复查依据）

| 角色 | 判定 | 数据范围 |
|---|---|---|
| 总部超级管理员 | 角色=Admin **且** ScopedDepartmentId 为空 | 不受限，全公司 |
| 受限用户（分公司管理员/文员/主管/班组长） | ScopedDepartmentId **有值**（IsScoped=true） | 只能看/管"自己部门 + 所有下级部门" |
| 普通员工 | 非 Admin、无范围 | 个人页只看自己 |

范围服务 `IDeptScopeService`（DeptScopeService.cs）语义：

- `GetVisibleDeptIdsAsync(cu)`：受限 → 自己+下级集合；不受限 → null（null = 不过滤，属设计）
- `CanAccessDeptAsync(cu, deptId)`：deptId 为 null 时受限用户恒 false（"没分部门的数据"受限不可见/不可操作）
- `ResolveEffectiveDeptId(s)Async`：把请求参数收窄到用户范围

**已文档化例外（不算漏洞）**：

1. 黑名单员工全公司共享（查黑名单时不过滤范围）；
2. "未分配部门"的员工/记录只总部可见；
3. 零部门绑定的考勤组视为全公司通用组（可见，且受限用户不可写）；
4. 无部门归属的待确认登记只总部可见。

## 3. 🔴 高危问题（H，建议上线前修复）

### H1 待确认登记"认领/确认"可跨分公司操作（读侧已修，写侧仍漏）

- **位置**：`Pages/Admin/UserManage.cshtml.cs` `OnPostCreateAsync`（RegistrationId 分支：约 224-228 认领、255-256 确认）+ `Services/Implementations/EmployeeRegistrationService.cs` `ClaimForConfirmAsync` / `MarkConfirmedAsync`（只按 `Id + Status==Pending` 条件，无部门归属）
- **现状**：列表**读侧已修好**——两处 `GetPendingAsync(...)` 均已传 `GetVisibleDeptIdsAsync` 结果，受限管理员列表只见本分公司登记。但**写路径仍是裸 id**。
- **攻击路径**：受限管理员构造 POST 把 `RegistrationId` 换成他司/无部门（HQ-only）登记的 id → `ClaimForConfirmAsync` 直接成功（登记被置 Confirmed）→ 取走对方登记的身份证照片 URL（可经角色级文件端点下载）→ 建档后登记被绑定到自己分公司新建账号；即使建档失败，对方登记也已被"消费"，真分公司管理员再也无法处理（状态≠Pending），登记人需重新扫码提交。
- **修复方向**：认领/驳回/确认前，按登记的 `DepartmentId` 过 `CanAccessDeptAsync`（null 部门对受限恒 false）；"认领+建档"放同一事务或建档失败回退状态。
- **状态**：未修复（2026-09-04 15:41 快照）

### H2 匿名考勤机推送可跨公司写打卡（设备接入链路完全没有隔离）

- **修复方向**：入库前校验打卡 PIN 对应员工 ∈ 该设备归属部门子树（或已通过 `UserZKDevice` 绑定该设备）；总部共用设备（`ZKDevice.DepartmentId` 为 null）需单独立口径（业务确认）。

- **位置**（同一套谓词，注释都写"关联部门**都**在自己范围内才可写"，实现却是 `deptIds.Any(∈范围)`）：

## 4. 🟠 中危问题（M）

### M1 待确认登记"驳回"越权

- **位置**：`UserManage.cshtml.cs` `OnPostRejectRegistrationAsync`（约 204-209）→ `EmployeeRegistrationService.RejectAsync`（约 128-138）
- **问题**：同文件其它按 id 操作（停用/拉黑/删除/重置密码等）都先过 `CanAccessUserAsync`，唯独驳回登记裸 id 直调；服务端只检查 `Status==Pending`，无部门范围条件。
- **影响**：受限管理员可把他司/无部门（HQ-only）登记驳回（跨公司数据破坏 + 存在性探测），登记人需重新扫码。
- **修复**：与 H1 同根，驳回前按登记 `DepartmentId` 过范围校验。

### M2 月度汇总"全库重算"入口无范围（两个调用点裸调全库）

- **根因**：`Services/Implementations/AttendanceService.cs` `GenerateMonthlySummaryAsync(int year, int month, int? onlyUserId = null)`（约 622-728）——no-id 重载的 candidateIds 查询（约 627-633）**无任何部门过滤**，直接全库在职/有记录/已有汇总用户重算并覆盖写 `MonthlyAttendanceSummaries`。
- **裸调调用点**：
  - `Pages/Report/MonthlyReport.cshtml.cs` `OnGetExportDetailAsync`（约 180 行）：受限管理员点"导出明细"前先全库重算一遍；
  - `Pages/Attendance/MyCalendar.cshtml.cs` `OnGetAsync`（约 43 行，页面仅 `[Authorize]`）：**任何登录员工**打开个人日历即可触发全库重算，year/month 由 URL 任意指定。
- **正确对照**：`Controllers/ReportController.cs`（约 70-74 行）先 `GetVisibleDeptIdsAsync` 圈出本范围 userIds 再逐个调 onlyUserId 重载。
- **影响**：越权改写/新建他司与总部的汇总行（若总部手工调整过的汇总可能被重算覆盖）；任意员工可反复触发全库重型负载。
- **修复**：服务层给写入方法加范围参数（防御性），或把 no-id 全库重载从受限/员工可达路径上撤掉，只允许后台任务与不受限总部触发。

### M3 审批"兜底审批人"可能自动指派到别的分公司

- **位置**：`Services/Implementations/ApprovalService.cs` `ResolveFallbackApproverAsync`（约 448-458，被 CreateApprovalStepsAsync 约 411/428 行调用）
- **问题**：兜底人从**全库** `Users.Where(IsActive && (Admin||Clerk) && Id != 申请人)` 里挑，优先"同 AttendanceGroupId"，匹配不到取 `managers[0]`（无 OrderBy）——没有任何公司/部门范围限制。
- **影响**：无直属上级、考勤组无审批人名单的员工（各分公司都会存在）的申请单可能被指派给**别家分公司**的受限管理员；审批人侧所有授权路径（pending 列表/详情/处理）只按 `ApproverUserId` 匹配，不校验其范围是否覆盖申请人部门 → 跨公司看 PII + 审批通过后回写申请人考勤。
- **现实性**：生产当前只有总部 admin，第一个创建的分公司管理员极可能成为全库 `managers[0]`，触发面真实。
- **修复**：兜底人限"申请人所属公司范围内"的 Admin/Clerk（按申请人 DepartmentId 的可见范围过滤）。

### M4 审批节点不随人员跨公司调岗失效

- **位置**：`ApprovalService.cs` `HandleApprovalAsync`（约 129-203）/`GetPendingForApproverAsync`（约 274-298）/`GetApprovalDetailAsync`（约 266-270）
- **问题**：审批节点生成后固定（ApproverUserId+状态），后续只校验节点归属人，从不复核申请人**当前** DepartmentId 是否还在该受限审批人的可见范围；审批链不随调岗重算/作废。
- **影响**：员工调出本公司后，原公司受限管理员仍可查看旧申请 PII 并审批，通过后回写（AttendanceService.UpdateAttendanceAfterApprovalAsync，约 864 行起，按 ApplicantUserId 直写）已属他司的考勤记录。
- **修复**：处理时复核申请人当前部门范围；或调岗时作废未决审批链。

### M5 公告"撤下"与"已读名单"可跨公司操作

- **位置**：`Services/Implementations/AnnouncementService.cs` `WithdrawAsync`（约 67-77）、`GetReadDetailAsync`（约 142-160）
- **问题**：两者都只校验 `isManager`（角色 Admin/Clerk，**含受限分公司管理员**）或本人发布，无任何部门范围/归属校验。
- **影响**：受限管理员可凭 id 撤下**任意**公告（他司部门公告、总部"全公司"公告），撤下后从所有分公司公告栏消失且无恢复入口；可拉任意公告的已读名单（他司员工姓名/工号/读状态，全公司公告=全量名册）。
- **注**：发布路径本身有服务端范围校验（Publish.cshtml.cs），漏的是撤下/查询。
- **修复**：撤下/查询前校验公告 ScopeType/ScopeId（或发布人）落在操作者范围内；All 范围公告仅总部可撤。

### M6 /iclock 匿名端点只靠 SN 白名单，可枚举

- **位置**：`Controllers/ZKDeviceController.cs`（约 32-61、155-207、265-301）
- **问题**：`IsKnownDeviceAsync` 只校验 SN 存在且启用，无来源 IP/网段绑定；对未知 SN 只有内存计数告警（约 46-61 行，阈值 20 次/10 分钟，只报错不拦截，重启清零），慢速枚举可持续探测。
- **影响**：持他司设备 SN 可匿名拉取该设备未确认命令队列明文（CommandText 含被绑定员工 PIN 与姓名）、抢先心跳"认领"或伪造 `devicecmd` 回执把命令标 Confirmed，使目标设备真实命令不再重发/被误确认——可中断他司向设备下发员工数据。
- **修复/加固**：确认设备固件是否支持签名/来源校验；至少把未知 SN 限制升级为硬限流+来源 IP 维度校验；SN 视为凭据的运维面（铭牌、旧设备流转）需管控。

### M7 敏感文件访问端点只按角色、不按范围（3 个子类）

- **位置**：`Controllers/PrivateFilesController.cs` `Get`（整文件 60 行）
  - `idcards` / `zkdevice` 分类（约 31-34）：任何 Admin/Clerk（含受限）可读**全库**身份证照片（含 `/idcards/registrations/{phone}/` 未确认登记件）与设备抓拍；
  - `faces` 分类（约 36-43）：任何管理员可读任意员工人脸参考照 `/faces/{userId}/`，以及全员远程打卡现场抓拍 `/faces/attempts/{yyyyMMdd}/`（该子目录第二段非数字，恒走管理员放行）；
  - `approvals` 等其它分类（约 44-45）：**仅登录即可读**任意审批附件（请假/出差证明等），普通员工、他司员工拿到 URL 即读。
- **现状说明**：文件名是随机 GUID，盲猜不可行，但端点完全放弃了第二道范围防线——"持有 URL 的任何人（满足角色）= 可读"；漏洞面随其它泄露面（H1、黑名单列表等）放大。
- **修复方向**：按文件归属做范围二次校验（idcards 按员工部门、faces 按 userId、approvals 按申请人+审批人）；分类改为显式白名单 + 默认 Forbid（当前 if-else 会导致未来新增分类静默落入"仅登录"档）。

### M8 `POST /api/admin/attendance-groups` 整实体绑定、零范围校验

- **位置**：`Controllers/AdminController.cs` `CreateAttendanceGroup`（约 275-282）
- **问题**：`[FromBody] AttendanceGroup` 直接 `Add + SaveChanges`，全程无 CanAccessDept/归属校验；EF 会把 body 里嵌套的导航集合（Departments/Approvers）一并落库。
- **影响**：受限用户可建"零部门通用组"（污染全公司可见命名空间）、把范围外用户塞进组审批人名单（后续该组员工的审批路由给范围外的人）、嵌套 Departments 携带任意 ParentId 在别家分公司树插垃圾部门。
- **注**：页面版 GroupManage 对受限用户有审批人/部门范围校验，API 没有——页面/接口口径不一致。
- **修复**：仿照页面版校验（勾选部门 ⊆ 可见范围、审批人 ⊆ 范围），或该端点仅 HQ 可用。

### M9 角色变更不即时生效（Cookie claim 陈旧）

- **位置**：`Middlewares/CurrentUserMiddleware.cs`（约 50-53、76-78）
- **问题**：每请求只从 DB 查 `IsActive / ContractCompany / ScopedDepartmentId`；`Role / DepartmentId / AttendanceGroupId` 取自**登录 Cookie 的 claim**。
- **影响**：HQ 把某人降权/调部门后，旧会话在 Cookie 有效期内仍按旧角色授权。特别地，"降权 + 清空范围"后：范围字段下一请求即失效，但 Role=Admin 声明仍在 → 可能被 `IsHqSuperAdmin`（Role==Admin && !IsScoped）判成不受限总部（提权方向的反向窗口）。IsActive 停用会即时踢线，是当前唯一即时兜底。
- **修复**：角色（乃至部门/考勤组）也改为每请求从 DB 读，与范围字段一致；或降权/调岗即踢线重登。
