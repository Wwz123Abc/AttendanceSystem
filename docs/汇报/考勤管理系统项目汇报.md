# 考勤管理系统项目汇报

> 汇报人：吴文喆　　时间：2026 年 10 月　　视角：功能与技术
> 本文是汇报 PPT 的文字版，供会后传阅和存档。数字截至 2026-10-26。

---

## 一、项目背景与目标

### 1.1 业务特点

系统服务于多分公司的临时工考勤：

- 多分公司、多考勤组并行运行；
- 白班、夜班、计时工三种用工方式并存；
- 员工流动大，每个月都有入职和离职。

### 1.2 原来的痛点

- 靠表格和人工核对，各处工时口径不统一；
- 加班、请假、补卡没有形成闭环；
- 发薪前要花大量时间复核数据。

### 1.3 系统目标

**一套口径算工时；从打卡到发薪表全程可追溯；规则可配置，变更后能自动对账。**

---

## 二、系统概览

### 2.1 四类使用者

| 使用者 | 主要能做什么 |
|---|---|
| 员工 | 手机人脸打卡；提交请假、加班、补卡、出差、转班申请；查看自己的记录 |
| 班组长 / 主管 | 审批五类申请（单条或批量）；给下属发公告 |
| 文员 / 管理员 | 排班、员工管理、报表导出、数据核对、饭点设置；文员和分公司管理员按"管理范围"只看得到自己部门的数据 |
| 系统自身 | 考勤机同步、每晚自动核对、申请超时作废、通知提醒 |

### 2.2 八个核心模块

打卡、排班、审批、工时计算、月度报表、员工管理、公告通知、智能助手。其中打卡、排班、审批、工时计算是主干，其余围绕它们提供管理和报表能力。

## 三、功能说明

### 3.1 打卡：三种方式，同一套结算

| 方式 | 说明 |
|---|---|
| 手机人脸打卡 | 接入人脸比对服务；先核对位置，通过后才打开摄像头；打卡前预告这次记为上班、午间还是下班 |
| 考勤机同步 | 熵基 PUSH 协议，设备序列号白名单；对打卡时间做合理性校验，异常时钟不入库；断网后补传、成批结算 |
| 补卡与更正 | 员工申请补卡并走审批；管理员可手动补卡，也可撤回；补卡规则在提交和回写时各校验一次 |

三种来源进入同一套归属和结算逻辑：先判断这次打卡属于哪一天，再按规则算工时。夜班跨零点的打卡归到上班那天。

### 3.2 工时与加班：几种场景，一套公式

| 场景 | 算法 |
|---|---|
| 普通班次 | 上下班时间差，扣默认饭点，不超过标准工时；午间窗口漏打只算上午 |
| 计时工（白班） | 最后一次打卡减第一次打卡，扣午饭 1 小时、晚饭 0.5 小时，不封顶；没有加班、旷工、早退 |
| 计时工（夜班） | 上班日 19:00 到次日 10:00 的打卡有效，归上班那天；扣 00:00–01:00 和 05:30–06:00 |
| 加班 | 只记班次上下班时间之外的部分；没排班时按近期班次兜底；补排班后自动对账 |
| 加班饭点 | 按班次设置，优先级为班次、考勤组、默认；文员和管理员都能改，但只限自己范围 |

所有路径统一向下取整到 0.5 小时，加班不足 0.5 小时不能提交。本地打卡、考勤机、补卡、班次重算走同一套函数，保证同一个人同一天，不论从哪条路径结算，结果一致。

**饭点按班次设置**：以前饭点只能按考勤组设，同组所有班次共用一套，导致个别班次被多扣 0.5 小时（如新能源客服的白班）。现在可在班次上单独设置，之前在报表里做的补偿因此取消。饭点只影响加班时长，不影响正班工时和请假。

### 3.3 计时工模式

成都鹰诺深圳分公司的临时工没有固定下班时间、没有加班申请。系统给考勤组增加了"计时工起始日"开关：起始日之前、之后互不影响，其他公司的算法不受任何影响。目前有 59 人按计时工计算，分属 2 个考勤组；夜班计时工已支持跨零点打卡。

### 3.4 审批与加班：规则在提交时就拦住

流程：员工提交 → 规则校验 → 多级审批 → 回写考勤 → 汇总刷新。

- **提交时拦截**：工作日加班不能和班次上下班时间重叠；同一时间段不能重复提交；计时工不能申请加班。
- **提交时间窗与有效期**：加班当天 24 点前提交，夜班可提前一天；补卡、转班申请 15 天没人处理自动作废。加班、请假、出差作废后员工无法再补交，所以不自动作废，只留给审批人处理。
- **不依赖排班**：没排班时用近期班次兜底；补排班后自动对账，加班只记班次之外的部分。

申请现有五类：请假、加班、补卡、出差、转班。

### 3.5 转班申请（新）

员工临时需要换班（如白班的人这几天上夜班），以前只能找管理员改排班。现在自己在"提交申请"里选"转班申请"，审批通过后系统自动改排班，并把已有打卡按新班次重新判断迟到、早退和工时，备注里写明原班次。

| 环节 | 规则 |
|---|---|
| 提交时校验 | 目标班次必须是自己考勤组里启用的；最早补报最近 3 天，最多提前 1 个月；一张最多连续 7 天；时间段不能重叠 |
| 生效时保护 | 已有批准请假、出差的日子不改班次；审批期间目标班次被停用则不改，并通知申请人 |
| 白夜互转提醒 | 已有打卡的白班与夜班互转，通知申请人和管理员核对打卡归属；转到休息日的空旷工记录改回正常 |

已知限制：转班不会自动给旧打卡重新归属，只提醒人工核对；审批通过后员工不能自己撤销。

### 3.6 管理与报表

- **月度报表**：发薪考勤汇总表、打卡时间表、员工原始打卡记录；支持按部门、按指定人员导出，分公司只能导自己范围内的人。
- **员工记录查询**：输入姓名，一页看全基本信息、考勤组、排班、考勤记录、原始打卡、审批单；没排班、旷工、打卡与排班对不上的会标红。
- **数据看板**：当天出勤实时统计，点卡片可看具体人员。
- **口径可追溯**：更新日志记录每次变更；口径登记表（已登记 206 条）记录每条计算规则的出处；数据订正先试算、先备份、单事务。

### 3.7 数据质量闭环

| 手段 | 说明 |
|---|---|
| 数据核对页 | 只读，最长查 63 天；每条记录按现行规则重算，与系统里存的工时和加班对比；疑点分类，可按类型筛选 |
| 每晚自动核对 | 凌晨 4 点后核对最近 14 天；只自动订正"结算时还没排班、后来补排班"的工时；其余只通知管理员；失败 30 分钟后重试 |
| 订正原则 | 线上订正先试算、先备份、单事务；手工订正过的加班不被夜里对账抹掉；深圳 GA 考勤组长期不排班，已从疑点中忽略 |

设计取舍是"能确定的自动改，不确定的只通知"：规则变更会让历史工时变化，所以夜里只订正补排班这一类，其余交给人判断。

### 3.8 权限与管理范围

- 角色：管理员、文员、主管、班组长、普通员工。
- 文员和分公司管理员受"管理范围"限制，只能看和管本部门及下级的数据；只有总部超级管理员不受限。
- 受限账号不能设置管理范围、不能操作总部管理员账号、不能修改多分公司共用的班次和通用考勤组。

## 四、技术说明

### 4.1 架构

单体应用，分层清晰：

| 层 | 内容 |
|---|---|
| 客户端 | 手机浏览器、管理后台、熵基考勤机 |
| 入口 | Nginx 反向代理，全程 HTTPS |
| 应用 | ASP.NET Core 8；Razor Pages 与接口；服务层（打卡、工时、审批、报表）；后台任务（旷工标记、提醒、汇总、每晚核对） |
| 数据 | MariaDB，EF Core 迁移；私有文件存储 |
| 外部服务 | 阿里云人脸比对；大模型驱动的智能助手（默认关闭） |

选择单体的原因：业务规则高度相关，工时、打卡、审批互相引用，拆开反而增加一致性成本。

### 4.2 技术栈

| 类别 | 技术 |
|---|---|
| 应用框架 | ASP.NET Core 8（Razor Pages 为主） |
| 数据访问 | EF Core 9 + Pomelo MySQL 驱动；数据库为 MariaDB |
| 认证 | Cookie 认证 |
| 考勤机对接 | 熵基（ZKTeco）PUSH 协议，设备主动推送 |
| 文档与日志 | NPOI（Excel 导出）、Serilog |
| 云服务 | 阿里云视觉智能开放平台（活体检测与 1:1 比对）、高德地图（打卡地点选点） |
| 智能助手 | DeepSeek 大模型，管理员和文员使用，密钥走环境变量 |

### 4.3 技术要点

- **规则集中**：工时公式、午间窗口、归属考勤日各只有一处权威实现，所有入口复用。
- **开关隔离**：新规则挂在考勤组开关上，只对开启的组生效，其他公司的算法不变。
- **后台任务**：定时标记旷工、发提醒、刷新月度汇总，并带重启后的补跑和幂等保护。
- **数据变更可控**：数据库迁移可重复执行；历史订正先试算、先备份、单事务、可回滚。
- **性能**：报表和对账一次性预加载，避免逐条查库；大批量操作限量或分批。
- **安全**：Cookie 加固、登录限流与锁定、文件按归属校验、全程无原生 SQL、考勤机序列号白名单。

## 五、质量保障

- 自动化测试 **558 个**，覆盖工时、打卡、审批、转班、报表、安全。其中 552 个通过；另有 6 个（私有文件访问 5 个、人脸参考照文件 1 个）在当前开发机上因环境原因失败，不是业务逻辑问题，需在标准环境补跑确认。
- 每次变更：更新日志、口径登记表、测试一起交付。
- 多轮代码审查，发现的问题逐条修复并补测试。
- 线上数据订正：先试算出清单，备份后在单个事务里写入。
- 发布后校验：服务状态、登录页、错误日志。

## 八、存在的问题与下一步

### 8.1 数据治理（需业务配合）

- 排班补全：新员工入职时直接排班，继续把未排班的人清零。
- 账号治理：没有考勤组的账号、长期没打卡的账号要分配或停用。
- 口径确认：多段午间窗口是否每段都要打。

### 8.2 技术债与加固

- 初始密码策略：不再统一初始密码，并强制首次改密。
- 图片组件升级：新版修复了已知漏洞，但需购买授权，待授权确定后升级；目前实际风险低（已不接受 TIFF 上传）。
- 转班后旧打卡自动重新归属，目前只提醒人工核对。
- 把三套"打卡归属考勤日"的实现收敛为一处。
- 在标准环境补跑 6 个环境相关的测试。

下一步的重点不是再加功能，而是让数据跟得上规则：排班补全、账号清理；技术上优先做密码策略和归属逻辑收敛。

## 九、总结

**一套口径，从打卡到发薪全程可追溯。**

- 一套口径：同一件事只有一处权威实现；
- 规则隔离：新规则按考勤组开关生效，不影响其他公司；
- 数据可追溯：更新日志、口径登记表、可回滚的订正流程。
