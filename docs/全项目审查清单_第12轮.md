## 1. 🟡 夜班补下班卡在审批时顺延到第二天，仍然能补出"未来的时间"

**问题**
- 上一轮 M5 加的检查只在**提交时**做，比较的是"申请日期 + 申请时间"是否晚于现在。
- 夜班（跨天班次）的下班卡是在**审批通过时**才顺延到第二天的（`ResolvePunchReplenishmentClockOut`），顺延之后没有再检查一次。

**复现** ✅复现
- 测试时刻约 09-29 07:14。夜班员工今天已有上班卡，申请"今天 06:54 下班卡"。
- 提交时比较的是 09-29 06:54，早于现在，检查通过。
- 审批通过后，下班卡落在 **09-30 06:54**（未来），这一班已经按 9 小时结算了。

**影响**
- 实际场景：夜班员工 21:00 提交"下班卡 08:00"，审批人一批，晚上 22:00 走人也按第二天 08:00 结算。
- 考勤机后来收到的真实下班卡（比如 22:00）会被"取更晚的那次"规则忽略。

**位置**
- `Services/Implementations/ApprovalService.cs` 约 64 行：提交时的检查
- `Services/Implementations/AttendanceService.cs` 约 1297 行：`UpdateAttendanceAfterApprovalAsync` 补卡分支里的顺延
- `Services/Implementations/AttendanceService.cs` 约 467 行：`ResolvePunchReplenishmentClockOut`

**改法**（两处都改：提交时就能提示员工；审批时兜底）

① 提交时，用和审批回写**同一个函数**算出最终的打卡时刻再比较：

```csharp
// ApprovalService.SubmitApprovalAsync → case ApprovalType.PunchReplenishment 里，替换原来那句检查
var punchAt = dto.PunchDate.Value.ToDateTime(dto.PunchTime.Value);
if (dto.PunchType == PunchType.ClockOut)
{
    // 跟审批回写（UpdateAttendanceAfterApprovalAsync）同一套顺延规则：夜班下班卡、早于上班卡的凌晨时间会落到第二天
    var existingClockIn = await db.AttendanceRecords
        .Where(r => r.UserId == applicantUserId && r.WorkDate == dto.PunchDate.Value)
        .Select(r => r.ClockInTime)
        .FirstOrDefaultAsync();
    var shiftForPunch = await db.ShiftAssignments
        .Where(a => a.UserId == applicantUserId && a.WorkDate == dto.PunchDate.Value)
        .Select(a => a.ShiftSchedule)
        .FirstOrDefaultAsync();
    punchAt = AttendanceService.ResolvePunchReplenishmentClockOut(
        dto.PunchDate.Value, dto.PunchTime.Value, existingClockIn, shiftForPunch);
}
if (punchAt > DateTime.Now)
    throw new InvalidOperationException($"补卡时间 {punchAt:MM-dd HH:mm} 还没到，请填写真实已经发生的打卡时间（夜班下班卡会算到第二天）");
```

> 这里直接查库，不走 `attendanceService.GetShiftAssignmentAsync`，因为测试用的 `FakeAttendanceService` 没有实现那个方法。

② 审批回写时兜底（员工提交后，上班卡可能才补进来，顺延结果会变）：

```csharp
// AttendanceService.UpdateAttendanceAfterApprovalAsync → 补卡分支，算完 punchDt 之后、写回 record 之前
```

- 这里抛出的异常会让整个审批事务回滚（`HandleApprovalAsync` 外面包了事务），数据不会改一半。
- `PendingApproval.cshtml.cs` 的单条"通过"（`OnPostApproveAsync`）现在没有接异常，会跳到全局错误页。建议补一个 `try/catch (InvalidOperationException ex) { Message = ex.Message; IsSuccess = false; }`，让审批人在页面上直接看到原因。批量审批已经有 `catch`。

## 2. 🟡 新饭点规则下，班次"标准工时"和实际整班工时对不上

**问题**
- 2026-09-29 起，工时改成"跟 4 个固定饭点时段的重叠部分不算"（12:00-13:00、17:30-18:00、00:00-01:00、05:30-06:00）。断崖问题确实消除了（在岗 6:00 和 6:01 现在都算 5 小时）。
- 但班次的"标准工时"是按旧算法手工填的，没跟着变。好几处计算拿标准工时当上限或当结果：
  - 半天假：当天工时上限 = 标准工时 − 请假小时数（`ApplyLeaveHoursCap`）
  - 全天假：每天请假小时数的上限（`ComputeLeaveHoursForDay` 的 `dailyCap`）
  - 出差：出差当天直接记标准工时

**新旧对比** ✅计算

| 场景 | 旧算法 | 新算法 | 变化 |
|---|---|---|---|
| 白班 08:30–17:30 | 8 | 8 | — |
| 白班 08:00–18:00 | 8.5 | 8.5 | — |
| 夜班 20:00–08:00 | 10.5 | 10.5 | — |
| 早班 06:00–14:00 | 7 | 7 | — |
| 中班 14:00–22:00 / 16:00–24:00 | 7 | **7.5** | +0.5 |
| 早班 05:00–13:00 | 7 | **6.5** | −0.5 |
| 夜班 22:00–06:00 | 7 | **6.5** | −0.5 |
| 白班下班接着加班 17:30–20:30 | 3 | **2.5** | −0.5（压到 17:30–18:00） |

**影响（例子）**
- 中班 14:00–22:00，标准工时仍是 7。员工请 18:00–22:00 的假（4 小时），下午实际干了 14:00–18:00，按新规则算 3.5 小时。
- 当天工时上限 = 7 − 4 = **3**，结果只记 3 小时，**少算 0.5 小时**。
- 同一个班，出差、全天假按 7 算，正常上一天班却是 7.5，三者不一致。
- 早班 05:00 开始、夜班 22:00 开始的正好相反：标准工时（7）比实际整班（6.5）多，出差、全天假会比上班多记 0.5 小时。

**另一个问题：本工资周期新旧算法混在一起**
- 本周期从 09-26 开始，09-26 到 09-28 已经落库的工时是旧算法算的。文档（口径登记表 §7.16 第 25 条）写了"存量不回填，由业务决定"。
- 但这几天只要发生补卡、审批回写、管理员手动补卡，或者月度汇总的"老数据补算"，就会按新算法重算。
- 结果是同一个周期里，哪天用新算法、哪天用旧算法，取决于这天有没有发生过重算，每个人都不一样。

**位置**
- `Services/Implementations/AttendanceService.cs`：约 1881 行 `UnpaidBreakWindows`；约 2009 行 `ApplyLeaveHoursCap`；约 1387 行请假的 `dailyCap`；约 1475 行出差记标准工时
- `Pages/Admin/ShiftManage.cshtml.cs` 约 287 行：保存班次时只检查标准工时在 0–24 之间

**改法**
1. **先请你拍板两件事**：
   - "白班下班接着加班少 0.5 小时"是否符合预期（这是 17:30–18:00 这个时段带来的，影响面最大）。
   - 09-26 起是否统一重算一次。
2. **复核现有班次的标准工时**。可以先用这条 SQL 把所有启用的班次列出来，逐个对照上面的算法：

```sql
SELECT g.GroupName, s.ShiftName, s.WorkStartTime, s.WorkEndTime, s.IsCrossDay, s.StandardWorkHours
FROM ShiftSchedule s
JOIN AttendanceGroup g ON g.Id = s.AttendanceGroupId
WHERE s.IsActive = 1
ORDER BY g.GroupName, s.WorkStartTime;
```

3. **防止以后再对不上**：保存班次时，按新规则算出整班工时，跟填的标准工时比一下。不一致就提示（或者直接自动填入）：

```csharp

var fullShiftHours = AttendanceSystem.Services.Implementations.AttendanceService.ComputeWorkHours(shiftStart, shiftEnd);
if (StdHours != fullShiftHours)
    throw new Exception($"按公司统一饭点时段扣减后，这个班次整班实际是 {fullShiftHours} 小时，标准工时请填 {fullShiftHours}（现在填的是 {StdHours}）；如果确实要不一样，请先跟财务确认口径");
```

> 接口 `AdminController` 的新建/修改班次（约 410、450 行）也要加同样的判断，两个入口要一致。

4. **如果决定回填**：写一个一次性的管理员操作（或脚本），把 09-26 起所有有上下班卡的记录，按当前规则重算 `ActualWorkHours`，已批准加班单的 `OvertimeHours`、已批准请假单的 `LeaveHours` 也一起重算，然后重新生成月度汇总。可以复用 `RecalcWorkHoursAfterManualPunchAsync` 的逻辑。

**验收**

- 中班 14:00–22:00 请 18:00–22:00 的假，当天工时应为 3.5，请假 4。

## 3. 🟡 安全：智能助手的"撤回"不经过角色层级检查

> 这条原属上一轮 M4 的一部分。上一轮的 S1 已经把角色层级检查放进 `UserService`，撤回就成了**唯一能绕过它的入口**，所以单独列出来。

**问题**
- 撤回员工类动作（启用/停用、拉黑、修改资料、调整角色）时，`RestoreUserRowAsync` 会把快照里的整行资料直接写回数据库，**包括角色和管理范围**，不经过 `UserService`，也不检查操作人现在管不管得到这个账号。
- 另外，它先保存字段，再调用启用/停用。启用/停用因为权限不足失败时，前面保存的角色、范围修改已经生效了，页面却显示撤回失败。

**复现** ✅复现
1. 分公司文员通过助手改了员工 X 的岗位，确认执行。
2. 之后总部把 X 提拔为分公司管理员（角色=管理员，管理范围=分公司）。
3. 文员对第 1 步的动作点"撤回"：显示成功，X 被还原成**普通员工**，管理范围被清空。

**影响**：文员不能直接动管理员账号，却能借撤回把管理员降级。撤回也没有时间限制，几天前的动作照样能撤。

**位置**：`Services/Implementations/AgentActionService.cs`，约 474–500 行 `RestoreAsync` → `RestoreUserRowAsync`

**改法**：在**改任何字段之前**做两道检查，一是目标现在的身份，二是快照里要恢复成的身份：

```csharp
// RestoreUserRowAsync 里，拿到 u（目标员工）之后、改任何字段之前
var op = await db.Users.AsNoTracking()
    .Where(x => x.Id == operatorUserId)
    .Select(x => new { x.Role, x.ScopedDepartmentId })
    .FirstOrDefaultAsync()
    ?? throw new InvalidOperationException("操作者账号不存在");

// ① 目标"现在"的角色/范围：管不到就不许撤回（挡住"对方后来被提拔成管理员"的情况）
if (!CurrentUser.CanManageAccountCore(op.Role, op.ScopedDepartmentId, u.Role, u.ScopedDepartmentId))
    throw new InvalidOperationException("无权撤回：该账号现在的角色超出你的管理权限（角色层级限制）");

// ② 快照里要恢复成的角色/范围：同样要管得到（防止借撤回把人恢复成管理员/不受限文员）
var snapRole  = row.TryGetProperty("Role", out var sr) && sr.ValueKind == JsonValueKind.Number
    ? (UserRole)sr.GetInt32() : u.Role;
var snapScope = RowInt(row, "ScopedDepartmentId");
if (!CurrentUser.CanManageAccountCore(op.Role, op.ScopedDepartmentId, snapRole, snapScope))
    throw new InvalidOperationException("无权撤回：要恢复成的角色超出你的管理权限（角色层级限制）");
```

- `RestoreUserRowAsync` 里抛出的异常会被 `UndoAsync` 的 `catch` 接住：撤回标记会被还原，页面显示"撤回失败：…"。
- 检查放在改字段之前，就不会再出现"改了一半"。
- 更稳妥的做法：把字段恢复和启用/停用放进同一个数据库事务（用 `db.Database.CreateExecutionStrategy()` 包一层，写法参考 `ApprovalService.HandleApprovalAsync`）。

**验收**（补回归测试）
- 复现步骤里第 3 步应该失败，X 仍是分公司管理员。
- 分公司文员撤回自己对普通员工做的修改，照常成功。

## 4. 🟢 智能助手生成动作时不检查角色层级

**问题**
- 上一轮修了"确认执行"那一步，现在执行时会被拦下。但"生成待确认动作"那一步仍然只检查部门范围。
- 文员让助手"重置总部超管的密码"，助手照样会生成一张【高风险】重置密码的卡片，确认时才报"无权操作该账号"。

**复现** ✅复现：总部文员对总部超管发起重置密码、彻底删除，分公司文员对分公司管理员发起重置密码，三张卡片都生成了，确认时都失败。

**影响**：不会造成实际损害，但会误导管理员；和批量确认一起用时，容易让人以为这些操作是被允许的。

**位置**：`Services/Implementations/AgentToolExecutor.cs`
- 约 702 行 `ResolveTargetAsync`：删除、拉黑、重置密码三个工具共用
- 约 666 行 `UserToggleProposeAsync`、约 1403 行 `EmployeeUpdateProposeAsync`、约 1472 行 `EmployeeBatchToggleProposeAsync`：各自有一份目标检查，也要补

**改法**（以 `ResolveTargetAsync` 为例，其余几处照同样方式补）：

```csharp
var u = await db.Users.AsNoTracking()
    .Where(x => x.Id == rawUserId.Value)
    .Select(x => new { x.Id, x.RealName, x.EmployeeNo, x.DepartmentId, x.Role, x.ScopedDepartmentId })
    .FirstOrDefaultAsync();
if (u is null) return (null, null, "错误：目标员工不存在");
if (visibleIds is not null && (u.DepartmentId is null || !visibleIds.Contains(u.DepartmentId.Value)))
    return (null, null, "错误：该员工不在你的管理范围内");

// 跟确认执行时 UserService 里同一道角色层级检查：文员不能动管理员、谁都不能动总部超管
var op = await db.Users.AsNoTracking()
    .Where(x => x.Id == operatorUserId)
    .Select(x => new { x.Role, x.ScopedDepartmentId })
    .FirstOrDefaultAsync();
if (op is null || !CurrentUser.CanManageAccountCore(op.Role, op.ScopedDepartmentId, u.Role, u.ScopedDepartmentId))
    return (null, null, "错误：无权操作该账号（角色层级限制）");

return (u.Id, $"{u.RealName}（{u.EmployeeNo}）", null);
```

> 批量启停（`EmployeeBatchToggleProposeAsync`）建议把管不到的账号从名单里剔除，并在返回文字里说明"已跳过 N 个无权操作的账号"。

**验收**：上面复现里的三次请求都直接返回"错误：无权操作该账号"，不生成任何待确认动作。

> ⚠️ **改完这条，`AttendanceSystem.Tests/AgentIntegrationTests.cs` 里有 3 个现有测试会失败，需要一起改**：
> `总部文员_不能通过助手重置总部超管的密码`、`总部文员_不能通过助手删除总部超管`、`总部文员_不能通过助手拉黑或停用总部超管`。
