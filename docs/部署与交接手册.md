## 2. 部署代码（最常用流程）

### 铁律：`appsettings*.json` 永远不能被覆盖

服务器上的 `appsettings.json` / `appsettings.Production.json` 存着真实的数据库密码与第三方密钥，**不在代码仓库里**（被 `.gitignore` 排除）。每次打包都必须把它们从上传包里删掉，确保解压不会把服务器上的真实配置换成占位内容。

### 第 1 步：本地编译打包

```bash
dotnet publish -c Release -o <临时发布目录>
cd <临时发布目录>
rm -f appsettings.json appsettings.Development.json appsettings.Example.json
tar czf deploy.tar.gz .

# 关键检查：这条命令有输出就说明没删干净，回到上一步
tar tzf deploy.tar.gz | grep -i appsettings
```

### 第 2 步：上传

```bash
scp -i ~/.ssh/attendance_deploy deploy.tar.gz ehr@172.16.9.62:/tmp/deploy.tar.gz
```

### 第 3 步：服务器上先备份网站目录，再解压覆盖

```bash
# 备份（回滚就靠它）
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo bash -c 'tar czf /root/att-backups/pre-deploy-webroot-\$(date +%Y%m%d%H%M%S).tar.gz -C /var/www/attendance-net .'"

# 解压覆盖
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo tar xzf /tmp/deploy.tar.gz -C /var/www/attendance-net && sudo chown -R www-data:www-data /var/www/attendance-net"

# 确认配置文件还在（应看到 appsettings.json / appsettings.Production.json / appsettings.Example.json）
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo find /var/www/attendance-net -maxdepth 1 -iname 'appsettings*'"
```

### 第 4 步：重启并确认

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo systemctl restart attendance-net"
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo systemctl status attendance-net --no-pager"        # active (running)
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo journalctl -u attendance-net --no-pager -n 40"     # 无 ERR/Exception
curl -s -o /dev/null -w "HTTP %{http_code}\n" https://adt.colibri.com.cn:15080/Login                     # 期望 200
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "rm -f /tmp/deploy.tar.gz"
```

> 重启瞬间偶尔有一条 Antiforgery 相关报错，是旧浏览器会话的正常现象，忽略。
> **重启后所有人的登录态会失效**（见第 6 节坑 12），需要重新登录。

## 3. 涉及数据库结构变更时（额外步骤）

**生产不会自动迁移**：`Program.cs` 里 `MigrateAsync()` 只在 `ASPNETCORE_ENVIRONMENT=Development` 下执行。生产必须手动跑 `migrate.sql`（`dotnet ef migrations script --idempotent` 生成的全量累积脚本，可安全重复执行）。

```bash
# 本地：新增迁移并重新导出脚本
dotnet ef migrations add <迁移名>
dotnet ef migrations script --idempotent -o migrate.sql

# 上传 + 备份 + 执行 + 清理
scp -i ~/.ssh/attendance_deploy migrate.sql ehr@172.16.9.62:/tmp/migrate.sql
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo bash -c 'mysqldump AttendanceDB > /root/att-backups/pre-migrate-\$(date +%Y%m%d%H%M%S).sql'"
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo bash -c 'mysql AttendanceDB < /tmp/migrate.sql'"
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "rm -f /tmp/migrate.sql"
```

**顺序：先迁移数据库、再部署代码**（新代码会用到新字段）。迁移完成后走第 2 节的完整流程。

**本地仓库的 `migrate.sql` 也要同步提交**（它是生产升级的输入，不提交就等于别人拿不到这步）。

## 4. 出问题怎么办（回滚）

### 代码回滚

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo ls -la /root/att-backups/"   # 找到部署前的备份文件
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo rm -rf /var/www/attendance-net/* && sudo tar xzf /root/att-backups/<备份文件名> -C /var/www/attendance-net && sudo chown -R www-data:www-data /var/www/attendance-net"
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo systemctl restart attendance-net"
```

### 数据库回滚

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo bash -c 'mysql AttendanceDB < /root/att-backups/<迁移前备份文件名>'"
```
⚠️ **会把数据库还原到备份那一刻，之后新产生的打卡/审批数据全部丢失**。拿不准就先别做，先找人确认。

> 补充：09-18 那次 `ActualWorkdays` 从 `int` 改成 `decimal` 的迁移，**回滚（`Down`）会把 21.5 变回 21/22**，丢掉那 0.5 天的精度——回滚前要知道这一点。

## 6. 必须知道的坑（踩过才知道）

1. **生产不会自动建表/改表**：忘了跑 `migrate.sql` 会出现"应用能跑、一碰新功能就报 SQL 错误"。
2. **MariaDB 全新安装时 `root@localhost` 默认 `auth_socket`**，.NET 走 TCP 连不上；要建专用应用账号（`caching_sha2_password`，只授权到 `AttendanceDB.*`），连接串不要用 root。
3. **GBK 编码坑**：熵基协议全程 GBK。`Program.cs` 注册了 `CodePagesEncodingProvider`，`ZKDeviceController` 里的 `Gbk` 静态字段是**读设备数据、回设备响应**唯一允许用的编码（用 ASCII 会把中文姓名变成 `?`）。
4. **请求体读取的隐藏坑**：设备上传若带 `Content-Type: application/x-www-form-urlencoded`，框架会先把请求体当表单读掉，控制器再读就是空的——**不报错，数据静默丢弃**。`Program.cs` 里对 `/iclock` 路径加了 `EnableBuffering()`，控制器读之前也会 `Position = 0`。新增设备端点务必照抄这个模式。
5. **打卡落库的并发竞态**：设备重发时两个请求可能都想插入同一条 `AttendanceRecord`，靠唯一索引拦后到者，抛 `DbUpdateException`。现在 `ProcessAttLogAsync` 外层最多重试 5 次（`ChangeTracker.Clear()` 后重跑），**前提是整个方法体重跑是幂等的**——改这段逻辑必须保证这一点。
6. **Z 设备白名单语义**：迁移到数据库表后是"表为空 = 全部拒绝"。**清空重建数据库后，重启服务之前必须先往 `ZKDevice` 表插入真实设备 SN**，否则设备心跳会被拒。
7. **人脸模板不会跨设备同步**（硬件限制）：系统只推"工号+姓名"，人脸模板存在设备本地，录一次只在那台设备有效。多设备互通需要厂商集中管理平台（等熵基答复）。
8. **PUSH 协议字段是"猜"出来的**：只有协议目录页 + 官方 Java 参考实现。`ATTLOG` 字段顺序（PIN/Time/Status/Verify，Tab 分隔）已真机验证，但换型号/固件未必一致——要改只改 `ParseAttLog` 一个方法。
9. **熵基协议不止一种"方言"**：老设备走经典 ADMS（`cdata` 握手 → `getrequest` 心跳），新设备走"acc"协议族（多一步 `registry`/`push`）。接新设备前先看它实际在调哪个路径：卡在反复重试 `cdata` 且伴随 `POST /iclock/registry` 404，就是 acc 族。
10. **"设备上报的签到/签退不可信"**：现在完全不看设备的 `Status`（只用于识别"外出/外出返回"），改成系统自己推算（当天第一次算上班、之后按班次午间窗口/离下班时间推算）。**已知权衡**：若以后某型号按键确实好用，要重新评估是否信任 `Status`。
11. **`appsettings.Production.json` 只能"合并着改"，绝不能整体覆盖**：曾因整文件替换丢掉了 `ConnectionStrings`/`Serilog`/`AppSettings`，服务崩溃重启循环。正确做法是用脚本读改写单个 key：
    ```bash
    python3 -c "
    import json
    p='/var/www/attendance-net/appsettings.Production.json'
    d=json.load(open(p)); d['新配置节']={'字段':'值'}
    json.dump(d, open(p,'w'), indent=2, ensure_ascii=False)"
    ```
    这个文件属于密钥文件，权限受限，该由人工自己动手。
12. **重启后所有人登录态失效**：Data Protection 密钥环没做持久化，每次重启都会生成新密钥，旧 Cookie/防伪令牌作废。属预期现象；要根治需 `AddDataProtection().PersistKeysToFileSystem(...)`（尚未做）。
13. **`AttendancePunch` 的唯一索引与"同一分钟重复打卡"**：`(UserId,PunchType,PunchTime)` 唯一索引 + 两条独立写入路径（`ZKDeviceSyncService` 与 `AttendanceService.PunchAsync`）。**改约束/索引时必须同时想到这两条路**。
14. **高德地图报 `INVALID_USER_DOMAIN`** 是 Key 的域名白名单没加当前域名（不是代码问题）；**白名单按域名管，每个域名都要单独加**。`AMapOptions` 两个值留空时地图选点按钮自动隐藏，不影响手动填经纬度。
15. **`POST /api/Attendance/punch` 是未收紧的老接口**：只挂 `[Authorize]`，直接调 `PunchAsync`，绕开远程打卡的人脸/开关/地点校验（当前无前端调用；用户尚未决定是否处理）。
16. **阿里云人脸识别是按次计费的**：每次远程打卡尝试都会真实调用"活体检测 + 1:1 比对"两次付费接口。`MaxAttemptsPerWindow`（5 次/10 分钟）只防刷。原来还有一道"每日上限成功 6 次/尝试 12 次"的成本闸门，**已于 2026-09-21 按业务要求取消，人脸识别打卡不再限制每人每天的次数**（`AliyunFaceOptions` 里的 `MaxSuccessfulVerificationsPerDay`/`MaxAttemptsPerDay` 已删除）。若远程打卡大规模推广，建议留意账单，实际调用量不再有每日上限兜底。
17. **`method="get"` 表单里放多个提交按钮，用 `name="handler" value="XXX"`，不要用 `formaction="...?handler=XXX"`**（GET 表单会丢弃 action 里的查询参数）——这个坑踩过两次。
18. **`AttendanceService.ComputeWorkHours` 的 6h/9h 阈值是"悬崖"**：在岗 6h00m 不扣午休、6h01m 扣掉整个午休（默认 60 分钟），多干一分钟反而少算近一小时工时；9h 扣晚餐同理。判断条件是 `rawMinutes > 6*60`，业务认可"宁少勿多"，不是 bug——有人质疑时直接查这里。
19. **`CalcClockInStatus` 用打卡自身日期推算"应上班时刻"**（不是记录归属的 `workDate`），所以跨天夜班零点后打卡不会标"迟到"（工时不受影响，只是状态标不出来）。`CalcClockOutStatus` 已正确用 `workDate`，两者不对称，属已知设计边缘。
20. **打卡时间显示精度两条链路不一致**：设备同步写 `ClockInTime/ClockOutTime` 用设备原始时间（带秒），App/远程路径是分钟精度。只影响显示，不影响工时计算。

## 9. 其它模块速览（接手项目该知道）

- **审批流程**：请假/补卡/加班/出差，一级/二级审批（`AttendanceGroup.ApprovalLevel`），审批人配置在"考勤组管理"；提交时同类型重叠单会被拦。
- **多打卡地点**：`AttendanceGroupLocation`，一组建多个地点、取最近的算有效范围（`HaversineMeters`）；远程打卡复用了这套机制。
- **员工自助登记**：`/Employee/SelfRegister`（匿名）扫码填资料 → 管理员在"员工管理→待确认登记"审核建号（走同一套 `CreateUserAsync`，会顺带同步考勤机）。
- **工号自动生成**：按部门找最近的"公司"节点（前缀写在 `UserService.CompanyPrefixByDeptName`），生成"前缀+5 位流水号"。
- **权限模型**：`ManagePolicy`（管理员+文员）、`ApprovePolicy`（+主管+班组长），定义在 `Program.cs`；数据范围一律由 `DeptScopeService` 决定。
- **远程打卡**：`AllowRemotePunch` 开关（默认关）+ 人脸参考照 + 定位校验（考勤组配了地点时）+ 成本闸门（两次成功识别间隔 30 秒，防手快连点；每日次数上限已取消）。
