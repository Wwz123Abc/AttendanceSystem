### 1. 请假时长按"0 点到 24 点"切分，不是按班次时间切分 `✅亲验` `⚠️需要你定口径`

**位置**
- `Services/Implementations/AttendanceService.cs:1704`（`ComputeLeaveHoursForDay`）、`:1724`（`HasLeaveOverlapForDay`）
- 调用方①提交时估算时长：`Services/Implementations/ApprovalService.cs:124-130`（`SubmitApprovalAsync`）
- 调用方②审批通过后写回：`AttendanceService.cs:1194-1255`（`UpdateAttendanceAfterApprovalAsync` 请假分支），其中 `:1253` 用 `ApplyLeaveHoursCap` 封顶当天工时

**问题**：跨天请假时，第一天的请假区间一直算到午夜 24:00，最后一天从 0:00 算起。比如 13:30~24:00，
扣掉午休和晚饭还有 9 小时，按标准工时封顶后就是一整天（8 小时）。

| 请假时间 | 系统算出 | 实际应为 |
|---|---|---|
| 周一 13:30 ~ 周二 12:00 | 8h + 8h = **2 天** | 约 1 天 |
| 09-09 14:00 ~ 09-11 12:00（口径登记表 §3 的验收例子） | 8h ×3 = **3 天** | 约 2 天 |
| 周五 08:30 ~ 下周一 17:30 | 8h ×4 = **4 天**（周六日也算请假） | 2 个工作日 |
| 夜班请一晚 20:00 ~ 次日 08:00（标准 11h） | 拆到两个日期：4h + 7h，各记 0.5 天 | 1 晚 |

**影响**（比多扣请假天数更严重）
- **当天上午的工时被清零**：周一上午其实上了班（08:30-12:00，3.5 小时），但周一记了 8 小时假，
  `ApplyLeaveHoursCap` 算出的工时上限是 8−8=0，上午的工时没了，`ResolveAttendanceDayCredit` 出勤也记 0。
  等于请 1 天假扣 2 天钱。这跟口径登记表 §4.4 验收第 3、4 条（半天假 + 半天上班要保留工时）的本意相反。
- **夜班第二晚的工时被砍**：第二天的记录被标成"请假"、记了 7 小时假，当晚真正上的夜班只能算"标准工时 − 7"（比如 11−7=4 小时）。
- **周末/节假日也被标成请假**，计入请假天数，还会把原来的"休假"状态覆盖成"请假"。

**注意**：口径登记表 §3 把"8+8+8=24 小时"写成了验收期望值，`AttendanceSystem.Tests/LeaveHoursTests.cs`
（`跨天请假_三天累计不再是套整段公式算出的畸高总数`）也是按这个写的——所以这是**口径本身**的问题，改之前要先定：
1. 请假时长是不是改成"只算跟当天班次上下班时间重叠的部分"（建议是）；没排班的日子按什么时间段算？
2. 休息日/节假日算不算请假？建议按假别区分：事假、病假、年假、调休不算；婚假、产假、丧假按自然日算（以公司制度为准）。

**改法（建议写法）**：`ComputeLeaveHoursForDay` 和 `HasLeaveOverlapForDay` 都改成按班次时间段取交集，两个调用方把当天的班次传进来
（两处都已经查好了 `leaveShiftsInRange`，直接 `GetValueOrDefault(d)` 即可）：

```csharp
/// <summary>这一天"可以请假"的时间段：有排班取班次的上下班时间（跨天班次下班顺延到第二天）；
/// 没排班时暂时沿用自然日 0:00~24:00（如果定了公司默认班次时间，改这里即可）。</summary>
public static (DateTime Start, DateTime End) ResolveLeaveWindow(DateOnly day, ShiftSchedule? shift)
{
    if (shift is null)
        return (day.ToDateTime(TimeOnly.MinValue), day.AddDays(1).ToDateTime(TimeOnly.MinValue));
    var start = day.ToDateTime(shift.WorkStartTime);
    var end   = day.ToDateTime(shift.WorkEndTime);
    if (shift.IsCrossDay) end = end.AddDays(1);
    return (start, end);
}

public static decimal ComputeLeaveHoursForDay(
    DateOnly day, DateTime leaveStart, DateTime leaveEnd, int lunchBreak, int dinnerBreak,
    decimal dailyCapHours, ShiftSchedule? shift)
{
    var (winStart, winEnd) = ResolveLeaveWindow(day, shift);
    var segStart = leaveStart > winStart ? leaveStart : winStart;
    var segEnd   = leaveEnd   < winEnd   ? leaveEnd   : winEnd;
    if (segEnd <= segStart) return 0;
    return Math.Min(ComputeWorkHours(segStart, segEnd, lunchBreak, dinnerBreak), dailyCapHours);
}

public static bool HasLeaveOverlapForDay(DateOnly day, DateTime leaveStart, DateTime leaveEnd, ShiftSchedule? shift)
{
    var (winStart, winEnd) = ResolveLeaveWindow(day, shift);
    var segStart = leaveStart > winStart ? leaveStart : winStart;
    var segEnd   = leaveEnd   < winEnd   ? leaveEnd   : winEnd;
    return segEnd > segStart;
}
```

按这个口径，白班 08:30-17:30 下"周一 13:30 ~ 周二 12:00"= 4h + 3.5h，各 0.5 天，合计 1 天；夜班请一晚只落在当晚那一天。
休息日/节假日是否跳过，在两个调用方的逐日循环里按假别加一个 `continue` 判断（判断休息日可复用 `IsShiftWeeklyRestDay` + `ResolveEffectiveHoliday`）。

**改完要同步**：`LeaveHoursTests.cs` 里跨天用例的期望值、口径登记表 §3 的验收期望值；存量请假记录要不要按新口径回填，需要单独决定（09-18 做过一次回填，可复用那个一次性工具的思路）。

### 2. 改排班、改班次、补节假日，都不会回头重算已有的考勤记录 `✅亲验`

**位置**
- 批量排班只改排班表：`Pages/Admin/ShiftManage.cshtml.cs:486-515`（`OnPostAssignAsync`）
- 修改班次（上下班时间、标准工时、休息日）：`ShiftManage.cshtml.cs:351-368`（`OnPostSaveShiftAsync`）
- 添加/删除假期：`Pages/Admin/HolidayManage.cshtml.cs`（`OnPostAddAsync` / `OnPostDeleteAsync`）
- 月度汇总的"老数据自愈"只重算工时还是 0 的记录：`AttendanceService.cs:792`
- 工时按排班下班时间封顶：`AttendanceService.cs:1612`（`ClampEffectiveClockOut`）

**问题**：迟到分钟、考勤状态、工时，都是**打卡那一刻按当时的排班算好存进库的**；之后改排班/改班次/加假期，这些值都不会变。
第 10 轮清单 §4 的计划是"等工厂给轮班表，补配中班、重排班"——照现在的代码，重排只影响以后的打卡，**历史记录不会被纠正**。

**影响**：不只是第 10 轮清单里说的"迟到数据不准"，**工时也少算了**：
- 实际 13:00-22:00 上班、却排成白班 08:30-17:30 的人，工时被截到 17:30，系统每天只算 **4.5 小时**；
- 按中班 13:00-22:00 算应该是 **8 小时**；
- 生产部这 163 人，每人每天少算约 3.5 小时（工资按工时结算）。

补节假日同理：那天已经被后台标成"旷工"的记录不会自动变回休假，但月度汇总的"应出勤"会变，两边对不上。
另外 `EnsureMonthlySummaryFreshAsync`（`AttendanceService.cs:859`）只比较考勤记录的更新时间，改排班/加假期后"我的日历"上的应出勤也不会刷新。

**改法**：做一个"按日期区间重算考勤"的管理功能，重排班/改班次/加删假期后提示管理员去点一下。下面是放在 `AttendanceService` 里的思路示例
（复用现有的 `RecalcWorkHoursAfterManualPunchAsync`，配合第 4 条的修改一起用；接口 `IAttendanceService` 里同步加声明）：

```csharp
/// <summary>按指定人员+日期区间，用最新的排班/班次/假期重算已有考勤记录的状态、迟到早退和工时，
/// 然后刷新受影响月份的月度汇总。用于重排班、改班次、补录节假日之后。返回处理的记录条数。</summary>
public async Task<int> RecalculateRecordsAsync(IReadOnlyCollection<int> userIds, DateOnly start, DateOnly end)
{
    var records = await db.AttendanceRecords
        .Where(r => userIds.Contains(r.UserId) && r.WorkDate >= start && r.WorkDate <= end)
        .ToListAsync();

    foreach (var r in records)
    {
        var shift = (await GetShiftAssignmentAsync(r.UserId, r.WorkDate))?.ShiftSchedule;
        if (shift is not null)
        {
            r.ScheduledStartTime = r.WorkDate.ToDateTime(shift.WorkStartTime);
            r.ScheduledEndTime   = r.WorkDate.ToDateTime(shift.WorkEndTime).AddDays(shift.IsCrossDay ? 1 : 0);
        }
        await RecalcWorkHoursAfterManualPunchAsync(r, r.UserId);
        r.UpdatedAt = DateTime.Now;
    }
    await db.SaveChangesAsync();

    foreach (var g in records.GroupBy(r => (r.WorkDate.Year, r.WorkDate.Month)))
        await GenerateMonthlySummaryAsync(g.Key.Year, g.Key.Month, g.Select(r => r.UserId).Distinct().ToList());
    return records.Count;
}
```

需要注意的边界：
- 上面只按记录里**已有的**上下班时间重算。"当天唯一一次打卡算上班还是下班"（`IsFirstPunchAfterShiftEnd`）是同步当时就定死的，
  排班变了可能要重新判断——需要的话，第二步可以改成从 `AttendancePunch` 原始流水重新推一遍上下班卡。
- `RecalcWorkHoursAfterManualPunchAsync` 对"节假日/出差"状态不重算工时；新加的假期要把当天无打卡的"旷工/未打卡"记录改成"休假"，
  有打卡的按设备同步的口径处理（状态改"休假"、不结算工时）；删掉的假期要对那天重新跑一次旷工判定。
- 人多日期长时循环里逐条查排班会比较慢，可以像 `GenerateMonthlySummaryAsync` 那样先整批查好放字典。

**在这个功能上线并对生产部重算之前，这批人的工时不建议直接用于发工资。**

### 3. 夜班"接上昨天记录"没有时间上限，漏打一次下班卡会连锁出错 `✅亲验` `⚠️时间窗要定`

**位置**
- 远程打卡：`AttendanceService.cs:77-92`（`PunchCoreAsync`）、`:331-355`（`GetTodayAttendanceAsync`，远程打卡页用它判断上班还是下班）
- 考勤机同步：`ZKDeviceSyncService.cs:137-144`（续接判断）、`:169-177`（上下班类型判断）

**问题**：只要"昨天排的是跨天班次、有上班卡没下班卡"，今天**任何时候**的打卡都会被接到昨天那条记录上。

**场景**：夜班员工周一 20:00 上班，周二早上忘了打下班卡——
1. 周二 20:00 他来上班打卡，这次卡被当成**周一的下班卡**（离周一应下班时间"够近"，判成下班）→ 周一显示正常、工时算满；
2. 周二这天没有任何记录 → 23:55 后台把他标成**旷工**并发提醒；
3. 周三早上的下班卡，因为周二没有上班卡，又被当成周三的上班卡……（之后的迟到判断也会跟着失真）

**同一个原因的另一种表现**：夜班下班时连刷两次脸（间隔超过 1 分钟），第二次会落到"今天"成为一条上班卡；
如果今天是休息日，月度汇总会凭空多出 1 天出勤和 1 次缺卡。

**改法**：给"接上昨天"加时间窗（小时数由你定，建议 4~6 小时），远程打卡、`GetTodayAttendanceAsync`、考勤机同步三处用同一个方法：

```csharp
// AttendanceService 里新增
/// <summary>夜班下班卡最晚能晚到什么时候还算"昨天那个夜班"的：昨天班次应下班时间之后这么多小时以内。</summary>
public const int NightShiftCarryOverHours = 6;

public static bool IsWithinNightCarryOver(DateOnly shiftDate, ShiftSchedule shift, DateTime punchTime) =>
    punchTime <= shiftDate.ToDateTime(shift.WorkEndTime).AddDays(1).AddHours(NightShiftCarryOverHours);
```

`PunchCoreAsync` 里把 `if (yesterdayAssignment?.ShiftSchedule.IsCrossDay == true)` 改成：

```csharp
if (yesterdayAssignment?.ShiftSchedule is { IsCrossDay: true } ys && IsWithinNightCarryOver(yesterday, ys, now))
```

`GetTodayAttendanceAsync` 同样改（时间用 `DateTime.Now`）。`ZKDeviceSyncService` 的续接条件末尾加上时间窗，并补上"下班后几分钟内的重复刷脸仍归昨天"：

```csharp
if (recordMap.TryGetValue((uid, yesterday), out var yesterdayRecord)
    && yesterdayRecord.ClockInTime != null && yesterdayRecord.ClockOutTime == null
    && shiftByUserDate.TryGetValue((uid, yesterday), out var yesterdayShift)
    && yesterdayShift?.IsCrossDay == true
    && AttendanceService.IsWithinNightCarryOver(yesterday, yesterdayShift, r.Time))
{
    workDate = yesterday;
}
// 夜班刚打完下班卡又连刷一次（几分钟内重复刷脸）：仍归昨天，后面会按"取更晚"更新下班时间
else if (recordMap.TryGetValue((uid, yesterday), out var yRec)
         && yRec.ClockOutTime is { } yOut && r.Time >= yOut && r.Time - yOut <= TimeSpan.FromMinutes(30)
         && shiftByUserDate.TryGetValue((uid, yesterday), out var yShift) && yShift.IsCrossDay)
{
    workDate = yesterday;
}
```

超出时间窗还没打下班卡的夜班记录，交给后台 `MarkAbsentAsync` 里已有的"夜班一直没打下班卡"兜底（`AttendanceBackgroundService.cs:255-301`）标"未打卡"即可。

### 4. 只补了一边卡的"旷工"日，同时算"旷工 1 天"和"出勤 1 天" `✅亲验`

**位置**：`AttendanceService.cs:1373`（`RecalcWorkHoursAfterManualPunchAsync` 上下班缺一个就直接 return）；
`:835`（月度汇总旷工天数按状态数）、`:935-940`（`ResolveAttendanceDayCredit` 出勤只看有没有上班卡）。

**问题**：后台把某天标成旷工后，员工只补了上班卡（或者管理员"手动补卡"只填了上班时间）：上班时间写进去了，
但因为没有下班卡，函数直接返回，状态还停在"旷工"。

**影响**：月度汇总和模板汇总表把这天既记 1 天旷工、又记 1 天出勤；如果是今天，看板上"出勤 + 旷工"会超过总人数。
员工只补一边、另一边没补或被驳回的话，这个矛盾会永久留在报表里。

**改法**（在 `:1373` 那行提前返回之前加）：

```csharp
// 只补了一边卡：人确实到过岗，不能继续挂"旷工"——跟后台 MarkAbsentAsync 里"只有下班卡→记未打卡"同一口径
if (record.AttendanceStatus == AttendanceStatus.Absent
    && (record.ClockInTime.HasValue ^ record.ClockOutTime.HasValue))
    record.AttendanceStatus = AttendanceStatus.NotPunched;
```

改完后这天会按"未打卡（缺卡）+ 出勤"统计，跟设备同步、后台任务的口径一致。建议补一条测试：旷工日只补上班卡 → 状态变"未打卡"、旷工天数不含这天。

### 5. 总部编辑分公司管理员时，可能误把他变成"不受限的总部超级管理员" `✅亲验`

**位置**
- `Pages/Admin/UserManage.cshtml:546-548`：「管理范围」下拉框只列出 `IsActive` 的部门
- `UserManage.cshtml:936`：编辑弹窗 `setScopedDeptId(data.scopedDeptId)` 回填

### 6. 分公司管理员编辑账号时，会静默改写对方的管理范围 `✅亲验`

**位置**：`Pages/Admin/UserManage.cshtml.cs:552-553`、`Controllers/AdminController.cs:195-199`（两处 `ApplyScopeAfterSaveAsync`）

**问题**：非总部管理员保存任何账号（新建或编辑），都会把对方的 `ScopedDepartmentId` 强制设成"操作者自己的范围"。结果：
- 编辑下级分公司的文员/管理员（范围 Y ⊂ X）→ 对方范围被**扩大**成整个 X；
- 编辑部门挂在本分公司下的总部文员（范围为空）→ 对方范围被**缩小**成 X（分公司账号把总部账号降了级）。

新建账号时钳到自己范围是对的（堵的是"分公司建出不受限文员"的提权链）；编辑时不应该无条件改写。

**改法（建议写法）**：`ApplyScopeAfterSaveAsync` 区分新建/编辑（`OnPostCreateAsync` 传 `true`，`OnPostUpdateAsync` 传 `false`；`AdminController` 同理）：

```csharp
private async Task ApplyScopeAfterSaveAsync(int userId, bool isCreate)
{
    var cu = HttpContext.GetCurrentUser()!;
    if (IsHqSuperAdmin(cu))
    {
        await userService.SetScopedDepartmentAsync(userId, ScopedDeptId);
        return;
    }
    if (!isCreate)
    {
        var currentScope = await db.Users.Where(u => u.Id == userId)
            .Select(u => u.ScopedDepartmentId).FirstOrDefaultAsync();
        // 对方原来的范围已经落在我的范围内（含相等）：保持不变，既不扩大也不改写
        if (currentScope.HasValue && await deptScopeService.CanAccessDeptAsync(cu, currentScope))
            return;
    }
    await userService.SetScopedDepartmentAsync(userId, cu.ScopedDepartmentId);
}
```

**要你定的一点**：范围为空的"总部文员"，分公司管理员到底该不该能编辑？建议不能——在 `CurrentUser.CanManageAccount`
（`Middlewares/CurrentUserMiddleware.cs:44-47`）里加上"非总部超管不能操作范围为空的文员"，这样上面的代码就不会碰到总部文员。

### 8. 审批单号按"今天第几单"计数，删过一张后当天会一直撞号 `✅亲验`

**位置**：`Services/Implementations/ApprovalService.cs:474-489`（`GenerateRequestNoAsync`，`:487` 计数 +1）；`:179-183`（撞号只重试 3 次）；`:192`（建审批节点失败时删掉刚建的单）

**问题**：单号 = 当天同类单据**条数** + 1。只要当天有一张**不是最后一张**的单被删掉，之后算出来的号就会一直落在已存在的号上。能触发的情况：
- 两人几乎同时提交，其中一张因为"没选有效审批人"被回滚删除（`:192`）；
- 删除了一个当天提交过申请的员工（申请单按外键级联删除）。

**影响**：3 次重试都撞号，**当天这一类申请全部提交失败**（员工看到"提交失败，请稍后重试"），要到第二天才自动恢复。

**改法**：流水号改成"取当天这一类已用到的最大流水号 + 1"：

```csharp
public async Task<string> GenerateRequestNoAsync(ApprovalType type)
{
    var prefix = type switch
    {
        ApprovalType.PunchReplenishment => "BK",
        ApprovalType.Leave              => "QJ",
        ApprovalType.Overtime           => "JB",
        ApprovalType.BusinessTrip       => "CC",
        _                               => "AP"
    };
    var head = prefix + DateTime.Now.ToString("yyyyMMdd");
    // 取当天这一类已用到的最大单号（流水号固定 4 位，按字符串排序就是按数值排序），不再按条数数，删过单也不会撞号
    var lastNo = await db.ApprovalRequests
        .Where(a => a.RequestNo.StartsWith(head))
        .OrderByDescending(a => a.RequestNo)
        .Select(a => a.RequestNo)
        .FirstOrDefaultAsync();
    var seq = lastNo is not null && int.TryParse(lastNo[head.Length..], out var n) ? n + 1 : 1;
    return $"{head}{seq:D4}";   // 如 QJ202609240001
}
```

`RequestNo` 上有唯一索引，`StartsWith` 会走索引；原来的"撞号重试 3 次"保留，用来兜两人同时提交的情况。
