# 生产服务器部署维护指南

> 说明：这份文档记录"如何把改好的代码更新到生产服务器上"的实际操作步骤，是这次开发过程中反复验证过的真实流程（不是理论上应该怎么做，是这段时间每次真的这么操作、确认没问题的）。面向要动手操作服务器的人，需要一点命令行基础。

---

## 一、你需要知道的几件事（开始前必读）

1. **生产服务器信息**
   - 内网地址：`172.16.9.62`（SSH 用这个）
   - 公网访问地址：`http://adt.colibri.com.cn:15080`（或 `http://116.7.225.116:15080`）
   - SSH 用户：`ehr`，有免密 `sudo` 权限
   - SSH 密钥：`~/.ssh/attendance_deploy`（连接时用 `-i` 指定）
   - 项目部署目录（网站根目录）：`/var/www/attendance-net`
   - 系统服务名：`attendance-net`（systemd 管理，`sudo systemctl` 操作）
   - 数据库：MySQL/MariaDB，库名 `AttendanceDB`

2. **最重要的一条铁律：`appsettings.json` / `appsettings.Production.json` 永远不能被覆盖**
   服务器上这两个文件里存着真实的数据库密码等敏感配置，是手工配置好、不在代码仓库里的（被 `.gitignore` 排除）。每次打包部署时，**必须把这几个文件从要上传的包里删掉**，确保上传解压不会把服务器上的真实配置替换成本地的占位内容。下面步骤 3 会具体讲怎么做，每次都要做，不能省。

3. **改动分两种，步骤不完全一样**
   - **只改了代码**（页面逻辑、接口、样式等，没有新增/修改数据库字段）：走"二、日常更新代码"就够了。
   - **改了数据库结构**（`Models/Entities` 下加了字段、新建了表）：除了更新代码，还要额外跑一遍数据库迁移脚本，见"三、涉及数据库结构变更时"。

## 二、日常更新代码（最常用的流程）

### 第 1 步：本地编译打包

在项目目录（`AttendanceSystem(1)/AttendanceSystem`）下执行：

```bash
# 用 Release 模式发布到一个临时目录
dotnet publish -c Release -o <临时发布目录>
```

### 第 2 步：从发布结果里删掉配置文件（关键，别漏）

```bash
cd <临时发布目录>
rm -f appsettings.json appsettings.Development.json appsettings.Example.json
```

### 第 3 步：打包并确认包里确实没有配置文件

```bash
cd <临时发布目录>
tar czf deploy.tar.gz .

# 确认一下：这条命令如果有输出，说明还没删干净，回第 2 步重新检查
tar tzf deploy.tar.gz | grep -i appsettings
```

### 第 4 步：上传到服务器

```bash
scp -i ~/.ssh/attendance_deploy deploy.tar.gz ehr@172.16.9.62:/tmp/deploy.tar.gz
```

### 第 5 步：服务器上先备份，再解压覆盖

先备份当前线上的整个网站目录（防止这次更新出问题需要回滚）：

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo bash -c 'tar czf /root/att-backups/pre-deploy-webroot-\$(date +%Y%m%d%H%M%S).tar.gz -C /var/www/attendance-net .'"
```

再解压新代码覆盖上去（因为第 2 步已经把配置文件从包里删掉了，这一步不会碰到服务器上真实的配置文件）：

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo tar xzf /tmp/deploy.tar.gz -C /var/www/attendance-net && sudo chown -R www-data:www-data /var/www/attendance-net"
```

解压完可以顺手确认一下配置文件还在、没被换掉：

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo find /var/www/attendance-net -maxdepth 1 -iname 'appsettings*'"
```
应该能看到 `appsettings.json`、`appsettings.Production.json`、`appsettings.Example.json` 三个文件都还在。

### 第 6 步：重启服务，让新代码生效

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo systemctl restart attendance-net"
```

### 第 7 步：确认服务正常启动

```bash
# 看服务状态，Active 那一行应该是 "active (running)"
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo systemctl status attendance-net --no-pager"

# 看最近的日志，正常情况下没有 ERR/Exception（重启瞬间偶尔会有一条 Antiforgery 相关的报错，
# 是旧浏览器会话的正常现象，忽略即可，不是新代码引入的问题）
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo journalctl -u attendance-net --no-pager -n 40"

# 从外部确认网站真的能访问（不是只在服务器内部通，公网也要能进）
curl -s -o /dev/null -w "HTTP %{http_code}\n" http://adt.colibri.com.cn:15080/Login
# 应该输出 HTTP 200
```

### 第 8 步：清理服务器上的临时文件

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "rm -f /tmp/deploy.tar.gz"
```

## 三、涉及数据库结构变更时（额外步骤）

如果这次改动在 `Models/Entities` 里加了字段/新表，本地要先生成迁移脚本：

```bash
# 生成一条新的迁移记录（<迁移名> 起一个描述这次改动的英文名，比如 AddUserBirthday）
dotnet ef migrations add <迁移名>

# 把所有迁移汇总导出成一份可以重复执行、不会重复建的 SQL 脚本
dotnet ef migrations script --idempotent -o migrate.sql
```

**部署顺序：先迁移数据库，再部署代码**（新代码可能会用到新字段，数据库要先有这个字段）：

```bash
# 1. 上传迁移脚本
scp -i ~/.ssh/attendance_deploy migrate.sql ehr@172.16.9.62:/tmp/migrate.sql

# 2. 迁移前备份数据库（哪怕迁移脚本本身是安全的加字段操作，备份不费事，出了意外能兜底）
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo bash -c 'mysqldump AttendanceDB > /root/att-backups/pre-migrate-\$(date +%Y%m%d%H%M%S).sql'"

# 3. 执行迁移
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo bash -c 'mysql AttendanceDB < /tmp/migrate.sql'"

# 4. 清理临时文件
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "rm -f /tmp/migrate.sql"
```

迁移做完之后，接着走上面"二、日常更新代码"的完整流程部署代码。

**为什么生产服不能像本地开发那样"启动时自动迁移"**：`Program.cs` 里写死了只有 `ASPNETCORE_ENVIRONMENT=Development`（本地开发）才会启动时自动跑迁移，生产环境必须手动执行 `migrate.sql`，这是故意的——数据库结构变更这种事，不应该在服务重启这种日常操作里"顺手"自动发生，得是一个看得见、可控的独立步骤。

## 四、出问题了怎么办（回滚）

### 代码回滚
每次部署前都会自动备份到 `/root/att-backups/pre-deploy-webroot-*.tar.gz`，回滚到上一版：

```bash
# 1. 先看有哪些备份，找到部署前那次的文件名
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo ls -la /root/att-backups/"

# 2. 清空当前目录，解压备份覆盖回去（<备份文件名> 换成实际文件名）
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo rm -rf /var/www/attendance-net/* && sudo tar xzf /root/att-backups/<备份文件名> -C /var/www/attendance-net && sudo chown -R www-data:www-data /var/www/attendance-net"

# 3. 重启服务
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 "sudo systemctl restart attendance-net"
```

### 数据库回滚
如果确认是数据库迁移导致的问题（比较少见，加字段/加表一般不会破坏什么），用迁移前的备份恢复：

```bash
ssh -i ~/.ssh/attendance_deploy ehr@172.16.9.62 \
  "sudo bash -c 'mysql AttendanceDB < /root/att-backups/<迁移前备份文件名>'"
```
**这个操作会把数据库还原到备份那一刻的状态，备份之后新产生的数据（打卡记录、审批等）会丢失，务必确认清楚再执行，拿不准就先别做，找人确认。**

## 五、常用运维命令速查

```bash
# 看服务是不是在运行
sudo systemctl status attendance-net --no-pager

# 重启（改完配置文件、或者怀疑服务卡住了用这个）
sudo systemctl restart attendance-net

# 停止 / 启动
sudo systemctl stop attendance-net
sudo systemctl start attendance-net

# 看实时日志（Ctrl+C 退出）
sudo journalctl -u attendance-net -f

# 看最近 N 行日志
sudo journalctl -u attendance-net --no-pager -n 100

# 只看报错
sudo journalctl -u attendance-net --no-pager -n 200 | grep -iE "err|exception|fail"

# 直接连数据库看看数据（进去之后就是普通 SQL 命令行）
sudo mysql AttendanceDB
```

## 六、安全注意事项

- **每次部署前，务必确认打包出来的文件里没有 `appsettings*.json`**（第 3 步的 `grep` 检查不能省），这是保护数据库密码等敏感配置最关键的一步。
- **每次部署/迁移前先备份**，哪怕觉得这次改动很小很安全——备份的成本远低于出问题后没法恢复的成本。
- 部署用的 SSH 私钥（`~/.ssh/attendance_deploy`）要妥善保管，不要传到聊天工具、网盘等地方。
- 如果要把部署权限交给别人（比如新来的技术人员），单独给他生成一把新的 SSH 密钥、加到服务器的 `authorized_keys` 里，不要直接把这把私钥文件发给他。
